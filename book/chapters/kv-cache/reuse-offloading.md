# 8.5 Prefix Caching 与 Offloading

前几节讨论单个请求内部如何保存历史。服务多个请求时，重复的 System Prompt、Few-shot 示例和对话前缀还会带来重复计算，有限显存也可能无法容纳全部可复用数据。Prefix Caching 复用相同前缀已经算出的 KV；Offloading 将 KV 放到 GPU 之外，需要时恢复或在数据所在设备上计算。两者分别处理重复计算与存储层级。

## 前缀复用的条件

在确定性的因果前向计算中，位置 $$j$$ 的表示只依赖它可见的前缀。若两个请求的 Token ID 序列在前 $$P$$ 个位置一致，且模型参数、位置、Mask 和相关计算配置一致，则这些位置的各层 KV 可以复用。[SGLang，§3、Appendix A.1](https://arxiv.org/html/2312.07104v2#S3)

这一条件可以逐层理解：相同的输入表示进入相同层，读取相同的可见前缀，产生相同的下一层表示。浮点实现还需保持可接受的数值一致性。

若加入动态选择器，其用于计算前缀的索引也必须由相同前缀确定；读取完整 Prompt 后再选择早期连接的流程需另行检查，见[7.4 基于内容的动态选择](../sparse-attention/dynamic-selection.md)。

缓存匹配因此需要关联影响 KV 的模型版本和配置；采用 Adapter 或多模态输入时，也应包含相应身份或内容信息。

| 输入关系 | 普通 Prefix Caching 的处理 |
| --- | --- |
| Token ID 前缀相同，计算配置一致 | 复用已计算的前缀 KV |
| 同一段文本出现在不同前文之后 | 后续表示受前文影响，重新计算或采用专门方法 |
| 文本相同，但 Tokenization 或模型配置不同 | 按实际模型输入及配置区分缓存 |
| 相同前缀，但所需 KV 已回收 | 重新计算，或从其他存储恢复 |

设请求长度为 $$N$$，实际命中的可复用前缀为 $$P<N$$。剩余 $$N-P$$ 个位置仍需计算，而且其 Query 需要读取缓存前缀。按每位置可见自身的 Causal Attention 计数，剩余的 Query–Key 配对数为：

$$
\sum_{i=P+1}^{N}i
=\frac{N(N+1)-P(P+1)}2.
$$

因此，命中前缀省去的是前缀位置的重复前向计算，剩余后缀与前缀之间的交互仍存在。若命中整个 Prompt，而缓存仅包含 KV，生成首个 Token 所需的末位输出还需要恢复或重新计算；具体快路径取决于系统保存的额外状态。

## RadixAttention 的前缀索引

SGLang 的 RadixAttention 用 Radix Tree 索引 Token 序列与对应 KV。共享前缀沿同一路径保存，分歧之后形成不同分支；新请求执行前缀匹配，完成后将新增部分加入索引。Radix Tree 的边可以表示一段 Token 序列，使连续、无分叉的路径得到压缩。[原论文 §3、Figure 3](https://arxiv.org/html/2312.07104v2#S3)

原论文采用叶节点优先的 LRU 回收，并以引用计数保护活跃请求使用的节点。保留父路径使其他分支仍能复用公共前缀。缓存与活跃请求共享内存池，所以保留更多历史前缀也会占用可供新请求使用的容量。

这里回收的是未被活跃请求引用、保留供跨请求复用的前缀 KV；它与活跃请求使用同一内存池，不要求额外复制。未命中的新请求可以重新计算前缀。8.4 讨论的淘汰则会在继续生成时限制当前请求能够访问的历史，两者的质量影响不同。

## Offloading 的数据路径

当 GPU 容量不足时，可以将部分 KV 保留在 CPU 内存等存储层。只要数据和位置元信息完整，迁移本身可以保持原有数值表示；若迁移同时使用量化或有损压缩，应单独评估这些近似。

FlexGen 将权重、激活和 KV 的放置与计算顺序共同优化，利用 GPU、CPU 和磁盘支持面向吞吐量的生成。其调度尝试重叠读取、写回与计算；KV 在 CPU 上时，也考虑在 CPU 执行相应 Attention 运算，以减少搬运整份历史的开销。[Sheng et al.，§4.1—§4.3](https://arxiv.org/html/2303.06865v1#S4)

| 场景 | 主要数据移动 | 影响的时刻 |
| --- | --- | --- |
| 恢复已缓存前缀 | 将命中前缀载入执行设备 | 新请求进入 Prefill 前后 |
| 恢复暂停请求 | 载入该请求继续计算所需的 KV | 请求恢复时 |
| 逐层读取外部 KV | 各层计算前读入历史，保存新增数据 | 可能影响每一步 Decode |
| 在 CPU 处理部分 Attention | 传递 Query 等输入及计算结果 | 对应层的前向计算 |

一次前缀载入可以在后续计算中持续使用；逐步从 CPU 读取完整历史则会重复支付传输成本。报告 Offloading 效果时，应说明数据在哪个层级驻留、迁移频率，以及哪些运算与传输重叠。

## 复用与迁移的成本比较

设一次恢复需要搬运 $$D$$ 字节，有效带宽为 $$B_{\mathrm{eff}}$$，固定启动和协调时间为 $$\tau$$，则可以用简化模型估算：

$$
T_{\mathrm{load}}\approx \tau+\frac{D}{B_{\mathrm{eff}}}.
$$

将它与同一前缀、同一负载下的重算时间比较，才能判断从外部缓存恢复是否合算。数据布局转换、反量化和等待时间也应计入实际测量。这个模型描述单次传输，不能直接推出请求延迟或整机吞吐量。

如果计算和传输可以完全重叠，阶段耗时接近两者的较大值；若存在串行依赖，则接近二者之和。实际调度还受共享带宽、缓冲容量和数据依赖约束。Prefix 命中率相同的两种方案，也可能因缓存驻留位置和调度方式不同而产生不同延迟。
