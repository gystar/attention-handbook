# 8.6 缓存策略与服务性能

缓存优化需要同时回答三个问题：能容纳多少活跃请求，每次迭代需要多少计算与数据访问，以及用户等待多久。较小的 KV Cache 可以扩大可调度空间，但最终收益还取决于请求长度、到达过程、缓存命中和调度策略。

## 容量预算与迭代调度

在固定设备上，模型权重、执行所需的临时空间、通信缓冲和 KV Cache 共同占用显存。给 KV 留出的预算应以实际运行峰值为依据；8.1 的有效数据量只覆盖其中一部分。分页、共享和量化改变可容纳的缓存数量，也改变哪些请求能进入执行批次。

Continuous Batching 在迭代边界更新批次：完成的请求退出，满足资源条件的新请求进入。请求在系统中的数量与本次迭代处理的 Token 数是不同的量；一个 Decode 请求通常贡献一个输入位置，一个 Prefill 请求可以贡献许多位置。长 Prefill 与已有 Decode 共享执行资源时，可能拉长正在生成的请求的输出间隔。

Sarathi-Serve 将 Prefill 分成多个 Chunk，在每次迭代先安排正在进行的 Decode，再用剩余 Token Budget 安排 Prefill。Chunked Prefill 保留跨 Chunk 的 KV 和因果关系；后面的 Chunk 仍访问前面的历史。论文同时指出，小 Chunk 可能增加 KV 读取和启动开销，因此预算需要结合延迟目标与硬件实测确定。[Agrawal et al.，§4.1—§4.3、Algorithm 3](https://arxiv.org/html/2403.02310v3#S4)

例如，在本书构造的调度算例中，单次迭代预算为 256 个位置，已有 32 个 Decode 请求各处理一个位置，则最多还能安排 224 个 Prefill 位置。这个计数仅描述批次组成；不同历史长度下，处理相同数量的位置仍可能具有不同的 Attention 成本。

## 首次响应与连续输出

设请求在 $$t_0$$ 到达，第 $$i$$ 个输出 Token 的观测时间为 $$t_i$$，共输出 $$m$$ 个 Token。本节按同一观测端的时间定义：

$$
\mathrm{TTFT}=t_1-t_0,\qquad
\mathrm{ITL}_i=t_i-t_{i-1}\quad(i=2,\ldots,m).
$$

TTFT（Time to First Token）包含首次输出之前的等待；ITL（Inter-token Latency）描述连续输出的间隔，相关文献也使用 TBT（Time Between Tokens）。Sarathi-Serve 将首 Token 延迟与后续间隔分别评价。[§2.4](https://arxiv.org/html/2403.02310v3#S2.SS4)

当 $$m\ge2$$ 时，平均间隔为：

$$
\overline{\mathrm{ITL}}=\frac{t_m-t_1}{m-1}.
$$

平均值可能掩盖一次较长的停顿。应同时报告分位数，并说明统计对象是单个 Token 间隔、每请求平均间隔，还是每请求最坏间隔。客户端观测还可能包含传输与缓冲；服务端 kernel 时间应另列，保持各方案的计时边界一致。

| 指标 | 回答的问题 | 必须说明的口径 |
| --- | --- | --- |
| TTFT | 多久开始输出 | 是否含排队、网络和前缀恢复 |
| ITL / TBT | 连续输出是否平稳 | 观测端、样本单位及分位数 |
| End-to-end Latency | 请求多久完成 | 输入输出长度、终止条件 |
| Output Tokens/s | 单位时间产生多少输出 | 是否排除输入 Token、统计区间 |
| Requests/s | 单位时间完成多少请求 | 工作负载及失败请求处理 |
| 满足 SLO 的服务容量 | 延迟约束下能承担多大负载 | SLO 阈值、分位数及负载生成方式 |

SLO（Service Level Objective）是预先约定的服务目标。例如，可以要求 TTFT 和 ITL 的指定分位数均低于阈值，再比较系统能持续承受的请求到达率。仅提高输出吞吐量，同时让等待队列不断增长，不能证明满足该服务目标。

## 缓存收益的来源与代价

| 策略 | 主要收益来源 | 同时计入的代价 |
| --- | --- | --- |
| PagedAttention | 按需分配、减少空间浪费、支持共享 | 块表访问、尾块空槽、复制 |
| Quantization | 减少编码后的存储与读取字节 | 参数、高精度部分、解包与误差 |
| Token Selection / Eviction | 减少可读取或保留的位置 | 评分与整理、信息损失 |
| Prefix Caching | 避免重复前向计算 | 保留空间、匹配与恢复、未命中 |
| Offloading | 使用其他存储层的容量 | 数据传输、同步与等待 |

量化方案应同时记录真实分配容量和解码时间；Prefix Caching 应报告冷启动与缓存预热后的结果，并区分按请求统计的命中率和按 Token 统计的复用比例。共享前缀长短不同，二者可能相差很大。

## 可比较的工作负载与质量条件

比较缓存策略时，至少固定模型与权重版本、硬件及并行配置、输入输出长度分布、请求到达过程和采样条件。缓存策略会改变输出时，还应检查长度变化是否影响时间结果；必要时分别提供固定长度性能测试与自然终止的任务测试。

对不同问题使用不同对照：

- **容量变化**：记录实际分配量、峰值、活跃请求数，以及是否发生抢占、重算或迁移。
- **调度变化**：保持请求轨迹，记录 TTFT、ITL 分布、排队时间和完成率；说明开环到达率或闭环并发数。
- **复用变化**：保留重复前缀的实际分布、请求顺序和缓存初始状态，测量命中后节省的计算与恢复成本。
- **有损策略**：在相同任务上报告质量，覆盖长生成、远距离检索和任务变化；分开比较位宽、保留预算与策略本身。

消融时逐项开启量化、共享、淘汰和迁移，再测试组合。若组合后收益改变，应检查是否由缓存格式不兼容、额外副本、评分开销或新的带宽瓶颈引起。
